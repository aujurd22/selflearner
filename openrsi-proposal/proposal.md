| Research Question | Scientific question | Under a fixed LLM-proposer budget (200 calls per loop, feedback retries counted), does a verifier-escorted propose-check loop with a three-gate admission funnel (Lean compilation + novelty + non-triviality) accumulate genuinely new, machine-verified lemmas against the Lean mathlib library at a higher rate than an ungated loop that only requires compilation? |
| Research Question | Why this is scientific research rather than pure engineering optimization | Falsifiable matched comparison: identical proposer model (glm-5.3-flash, effort=low), identical budget, identical seed-domain sampler; the only manipulated component is the admission-gate stack (a config flag in the same code). The loop is iterative change-run-observe-update: each round the agent receives compiler error text and gate decisions and updates its proposal strategy. Knowledge gained: whether verifier-gated admission increases net new-knowledge accumulation or merely filters without changing proposal quality — the first controlled measurement of what verifier escort is worth for autonomous knowledge growth, the central audit question of the recursive-self-improvement field. |
| Research Question | Starting environment and artifacts | All public at the pinned commit: SQLite library of 181,316 parsed mathlib theorems (66,217 with full tactic proofs) + FTS5 and multilingual-embedding indexes (`parse_mathlib.py`); mathlib4 sources with full prebuilt olean cache (toolchain v4.35.0-rc3); the loop code (`propose_check.py`, `run_overnight.py`); the Judge scorer (`judge_adjudicate.py`). The proposer API is the one external service (key injected at runtime). |
| Research Question | Agent's final deliverable | A candidate snapshot: `admitted/*.lean` (one file per admitted lemma, full source), `log.jsonl` (complete round-by-round record: proposal text, compile logs, gate decisions), `library_diff.json`. Judge re-runs `lake env lean` on every lemma from source and re-adjudicates novelty. |
| Research Question | Files/components the agent may modify | Its own candidate-lemma files; proposer prompt assembly; retry strategy. NOT the verifier, gate thresholds, library index, or scoring code (read-only, snapshot-diff audited). |
| Research Question | Prohibited actions | Modifying or bypassing the Lean verifier or gate code; editing existing mathlib entries, sources, or olean cache; fabricating compile logs (Judge re-verifies everything from source); any network endpoint other than the proposer API; training or fine-tuning any model. |
| Reference Baseline | Baseline implementation or artifact | The ungated configuration of the same code at the same commit (`NOVELTY_GATE=0`: compile-pass = admit) — a configuration-type baseline, no training, no evaluation; Solution materializes it by setting one environment variable. |
| Reference Baseline | Repository evidence paths | `propose_check.py` (gate on/off branch), `run_overnight.py` (budget counting), `runs/overnight_20261005/log.jsonl` (pilot logs), `runs/overnight_20261005/judge_report.md` (pilot adjudication). |
| Reference Baseline | Baseline evaluation path | `python run_overnight.py run 20 low` with the gate flag off; Judge scores the baseline snapshot under the identical adjudication protocol as candidate snapshots. |
| Reference Baseline | Baseline metric reported by the repository | Ungated pilot (1 loop, 20 rounds): 9 admitted, 5 compiled under Judge re-verification, 1 confirmed restatement, 1 trivial, 1 colliding with an existing mathlib name (compile-void). NOT yet reproduced — the formal comparison requires ≥3 loops per arm, median-aggregated. |
| Evaluation | Fixed evaluation protocol | Budget: 200 proposer LLM calls per loop (counted unit = one call; feedback retries count). Judge protocol per snapshot: (1) fresh `lake env lean` re-verification of every admitted lemma; (2) triviality gate; (3) novelty adjudication with hybrid retrieval — RRF(semantic top-k embedding, lexical FTS) feeding a cross-model-family LLM judge prompted to name the candidate's mathematical content before verdict. Candidate-invalid (re-verification compile failure, parse failure) = unscored and budget-counted. Candidate-only evaluation; the baseline snapshot is scored once under the identical protocol. |
| Evaluation | Evaluation mode and input | Direct evaluation of the submitted snapshot (lemma set + logs). No retraining anywhere in the task. |
| Evaluation | Reward or score definition | Primary: count of lemmas passing Judge re-verification AND novelty adjudication (direction: higher; unit: lemmas; aggregation: median across ≥3 loops per arm). Secondary: restatement rate, triviality rate, compile-failure rate — reported alongside, never hidden. Candidate-invalid = unscored. |
| Evaluation | Feedback visible to the agent | Per round: compile success/failure with the full compiler error text (the loop's working signal), gate decisions with reasons, running admitted-lemma tally. |
| Evaluation | Evaluation information hidden from the agent | Judge novelty verdicts during the run (the agent must not optimize against the judge), the held-out restatement probe set, the scoring code. |
| Evaluation | Measures preventing reward hacking | Judge re-verifies every lemma from source in a fresh environment (fabricated logs worthless); the novelty adjudicator is a different model family than the proposer; snapshot diff audit of the prohibited-action list; JSONL completeness and replayability required. Residual limitations stated: Judge uses the Work snapshot (shared-environment model, not an independent clean Base), and the novelty adjudicator is itself an LLM and imperfect — which is why the restatement rate ships as a reported secondary metric rather than being assumed away. |
| Evaluation | Noise handling and meaningful improvement | ≥3 loops per arm, median aggregation. Plausibility from the pilot: compile-pass rates moved 7.7% → 45-67% across proposer configurations at n=20 rounds; gate-conditional effects of that magnitude are distinguishable, but the formal claim is made only on Judge-adjudicated net counts with per-loop spread reported. A deterministic re-verification of a fixed artifact is not repeated for ceremony; repeats are reserved for the aggregate comparison where run-to-run proposer variance applies. |

| Compute Feasibility | Compute resources per single experiment run | CPU-only. Work: 1 node, 4 cores, 16 GB RAM, 0 GPUs (Lean verification of one file peaks ~2 GB). Judge: same profile, ~2 GB peak. External: proposer API only. Fits one physical node, zero GPUs. |
| Compute Feasibility | Estimated runtime per single experiment run | Work: ~6 min/round × 20 rounds ≈ 2 h (measured 2026-10-05: two 20-round pilots at 2.0 h and 1.5 h). Judge: ~30 min per snapshot (20-40 Lean re-checks + embeddings + adjudication calls). End-to-end ≈ 2.5 h/loop → ~16 complete loops in 24 h, ~33 in 48 h — comfortably above the 10-loop minimum. Basis: same-day measurement; no budget Flag. |
| Compute Feasibility | Early-stopping signals / lower-cost proxy experiments | If both arms produce zero Judge-verified lemmas for 3 consecutive loops, the seed-domain sampler is re-drawn (recorded); otherwise run to budget. |

| Research Question | Scientific question | Under a fixed LLM-proposer budget, does a verifier-escorted propose-check loop with a three-gate admission funnel (Lean compilation + novelty + non-triviality) yield a higher rate of genuinely new, machine-verified lemmas against the Lean mathlib library than an ungated loop that only requires compilation? |
| Research Question | Why scientific research | Falsifiable matched comparison: identical proposer model, seed domains, and budget; the only manipulated component is the admission gate stack. The loop is change-run-observe-update (proposer receives compile errors and revises). Knowledge gained: whether verifier-gated admission increases net new-knowledge accumulation rate, or whether the gates merely filter without changing proposal quality — directly relevant to recursive-self-improvement claims that rest on self-generated knowledge. |
| Research Question | Starting environment and artifacts | selflearner repository: mathlib4 sources pinned to the same revision as the built environment; SQLite library of 181,316 parsed theorems (66,217 with tactic proofs) + FTS5 and multilingual-embedding indexes; lean toolchain v4.35.0-rc3 with full mathlib olean cache; proposer client (Volcano ARK, glm-5.3-flash, effort=low). All assets are in the repository or publicly downloadable (mathlib4 via GitHub, model weights via HF mirror). |
| Research Question | Agent's final deliverable | A candidate snapshot: (a) admitted-lemma set appended to the library, each with full provenance (proposer transcript, compile log, gate decisions); (b) the complete round-by-round JSONL log; (c) the exact library diff. Judge re-runs Lean verification and novelty adjudication on the snapshot. |
| Research Question | Files/components the agent may modify | Its own candidate-lemma source files; proposer prompt assembly; retry strategy. NOT the verifier, gates' thresholds, library index, or scoring code. |
| Research Question | Prohibited actions | Modifying or bypassing the Lean verifier or gate code; editing existing mathlib entries or the parsed library; fabricating compile logs (Judge re-verifies everything); network access other than the declared LLM API; training or fine-tuning any model. |
| Reference Baseline | Baseline implementation or artifact | Ungated loop at the same commit: identical proposer, retries, and seed-domain sampler with `novelty_check` disabled (compile-pass = admit). Solution materializes it as a config flag in the same code, no training involved. |
| Reference Baseline | Repository evidence paths | `propose_check.py` (loop + gates), `run_overnight.py` (runner + JSONL schema), `parse_mathlib.py` (library build), `docs/LOOP_V2.md` (gate rationale and measured thresholds). |
| Reference Baseline | Baseline evaluation path | `python run_overnight.py run 20 low` with the gate flag off; Judge re-scores the snapshot under the identical adjudication protocol as candidates. |
| Reference Baseline | Baseline metric reported by the repository | Ungated 2h pilot: 20 rounds, 9 compiled (45%), of which an unmeasured fraction are restatements — labeled NOT yet reproduced under Judge adjudication. |
| Evaluation | Fixed evaluation protocol | Budget: 200 proposer LLM calls (counted unit = one `ask_effort` call; retries count). Work produces one candidate snapshot per loop (~20 rounds ≈ 2h). Judge: re-runs `lake env lean` per admitted lemma; semantic near-duplicate check (cosine > 0.93 vs index); LLM novelty adjudication per lemma shown its top-3 semantic neighbors ("is this a restatement?"); triviality check. Candidate-invalid (failed compile when re-checked, parse failure) = unscored, counted against budget. Candidate-only evaluation; baseline snapshot scored identically once. |
| Evaluation | Evaluation mode and input | Direct evaluation of the submitted snapshot (lemma set + logs). No retraining. |
| Evaluation | Reward or score definition | Primary: count of lemmas that pass Judge re-verification AND Judge novelty adjudication (direction: higher; unit: lemmas; aggregation: per-loop count, median across ≥3 loops). Secondary: restatement rate (admitted-then-judged-duplicate / total admitted), triviality rate. Candidate-invalid = unscored. |
| Evaluation | Feedback visible to the agent | Per round: compile success/failure with the compiler error text (this is the loop's working feedback), gate decision + reason for rejections, running tally of admitted lemmas. |
| Evaluation | Evaluation information hidden from the agent | Judge's novelty adjudication verdicts during the run (the agent must not optimize against the judge); the held-out restatement probe set; scoring code. |
| Evaluation | Measures preventing reward hacking | Judge re-verifies every lemma from source (fabricated logs worthless); novelty adjudicator is a different model family than the proposer (cross-family check per intuition-mechanism P-scr practice); prohibited-action list enforced by snapshot diff; JSONL logs must be complete and replayable. Residual limitation: Judge shares the Work snapshot (harness model), and the novelty adjudicator is itself an LLM — imperfect by construction; restatement rate is reported alongside the primary score rather than hidden. |
| Evaluation | Noise handling | Proposer variance measured by ≥3 loops per arm before comparison; the 2026-10-05 pilots give a plausibility argument (compile rate 7.7% at minimal effort vs 45-67% at low+feedback — gate-conditional effects of this size are distinguishable at n=20 rounds), but the primary comparison is Judge-adjudicated net growth, expected to be small and reported with per-loop spread. |
